현재 배포 구조: 브라우저, 단일 FastAPI 컨테이너, 호스트 저장소와 외부 OpenAI API

시연 전 점검

  1. docker compose ps에서 spec2rtl-app이 healthy인지 확인한다.
  2. /api/health, ECSS PDF, 기존 PASS run과 저장 Q&A를 확인한다.
  3. API 키 값은 화면이나 터미널에 출력하지 않는다.
  4. 라이브 실행이 실패하면 기존 evidence를 사용하되 실패를 PASS로 설명하지 않는다.

5. 예상 질의응답

Q1. LLM이 RTL의 PASS/FAIL을 판정합니까?
아니다. PASS/FAIL은 Golden regression과 RTL compile/simulation의 22개 실행 판정이 생성한다. LLM은 연결된 근거와 기존 실행 결과를 설명한다.
Q2. 왜 SQLite를 사용했습니까?
현재 단일 사용자·18개 Requirement MVP에는 별도 DB 서버가 필요 없고 배포가 단순한 SQLite가 적합하다. Q&A 이력과 FTS5 Spec 색인에 사용했다.
Q3. Docker에는 무엇이 들어 있습니까?
FastAPI, 정적 UI, Golden Model, Icarus runner가 기본 단일 컨테이너에 있다. SQLite·run evidence·PDF·환경 파일은 호스트 mount로 분리했다.
Q4. OpenAI로 어떤 데이터가 전달됩니까?
선택 Requirement의 제한된 Spec·Golden·RTL·Test 발췌만 전달한다. 전체 PDF와 VCD, API 키는 전달하지 않는다.
Q5. Chapter 5.4는 어디까지 확장했습니까?
선정한 7개 후보를 모두 실행 카드로 편입했다. First Null은 실제 encoder D/S 출력으로, Null detection과 parity gate는 project-owned compliance RTL로 검증한다. imported top-level 통합은 별도다.
Q6. 재현성은 어떻게 확인했습니까?
새 Git checkout에서 Docker를 다시 빌드하고 FastAPI·SQLite 검색·source/JUnit 조회와 Golden/RTL 실행을 검증했다. 발견된 초기 SQLite 디렉터리 권한 문제도 수정 후 재검증했다.
Q7. 규모가 커지면 무엇을 먼저 바꿉니까?
simulation worker와 queue를 API 서버에서 분리하고, SQLite를 PostgreSQL로 전환한 뒤 run artifact를 별도 저장소로 이동한다.

실패 시 대응

  • Q&A 지연: 저장된 Previous questions와 기존 출처 링크를 시연한다.
  • Run 실패: 실패 단계 로그를 열고, 기존 PASS run의 JUnit과 waveform을 보조 증거로 제시한다.
  • PDF 미설치: catalog의 clause·page·excerpt와 연결 소스로 provenance를 설명한다.
  • Docker 비정상: 현장에서 재빌드를 반복하지 않고 상태와 health까지만 진단한다.

6. 한계, 확장 방향 및 결론

현재 한계

  • 새 Null/parity compliance RTL은 runner에 연결됐지만 imported spw_top에는 아직 인스턴스되지 않았다.

  • 단일 컨테이너에서 API와 simulation을 실행하므로 다중 사용자·장시간 작업 확장에는 제약이 있다.

결론

본 MVP는 “Spec → Golden → RTL → Test → Evidence → Q&A”의 연결을 실제 실행 가능한 형태로 증명했다. SQLite와 Docker는 단순 기술 나열이 아니라 이력·검색과 재현 가능한 배포에 사용됐으며, FastAPI는 UI와 검증·Q&A 기능을 하나의 명확한 API 경계로 제공한다.

부트캠프 발표에서는 기능 수보다 다음 세 가지를 중심으로 설명한다.

  1. Requirement 선택이 실제 소스와 검증 증거까지 일관되게 연결되는가.
  2. LLM 설명과 독립적인 실행 판정이 분리돼 있는가.
  3. 새 환경에서 Docker로 같은 동작을 재현할 수 있는가.
